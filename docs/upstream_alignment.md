# Where upstream wowsims is heading, and how this fork lines up with it

Written 15 September 2026, after the wowsims team said on Discord that an official Forever
fork will follow the beta once "some tech debt that's being worked on now" is resolved, and
invited cherry-picking from this fork. This is what that tech debt is, read from their
repositories, and what it means for anything they take from here.

## Which repository the official fork will come from

- `wowsims/classic`, the repository this fork started from, has had **no commits since our
  fork point (24 July 2026)**. Its open branches (`MageRipOut`, `PriestRipOut`,
  `WarriorRipOut`, `fix/refactor-sod-build`, `DeleteTankRogue`, ...) are all from late 2024
  and share no history with its current master; they are the original Season of Discovery
  rip-out, long finished. Nothing is being worked on there.
- `wowsims/mop` and `wowsims/tbc-new` are the live codebase, with commits daily through
  14 September. `tbc-new` is a TBC sim rebuilt this year on the MoP engine, by the same
  maintainers, and is the current template for "a new expansion sim". It keeps Classic-style
  talent trees.
- So the tech debt being resolved is the September 2026 refactor stream landing in `mop` and
  `tbc-new`, and an official Forever fork will almost certainly be cut from that codebase,
  not from `wowsims/classic`. Worth confirming with them; everything below assumes it.

Their GitHub issues could not be read from the environment this was written in (API access
is scoped to this repository); the commit history is the source here.

## The tech debt they are paying down (mop/tbc-new, 30 Aug - 14 Sep 2026)

1. **Spec pages are generated by vite**, not sed-ed into the tree by the makefile
   (`tools/vite/spec_pages.mts`; mop #1559). Exactly the debt that bit this fork in #79,
   where the makefile overwrote the hand-written BiS page with the template.
2. **The raid sim UI is gone** (mop #1556, "unsupported"). The Go raid engine
   (`RunRaidSim`) stays. This fork's DPS rankings page is built on the raid sim, see below.
3. **Combat log and timeline rewritten** on a data model: a two-pass log parser, filters
   built from the app's own dropdowns, chart.js replacing ApexCharts, a `VirtualList`
   replacing clusterize, tooltips built on first hover, a benchmark harness for it all.
4. **Dead code sweeps**: unused metrics symbols, stylesheet rules nothing matches,
   comments the code already says. Commit subjects are conventional:
   `type(scope): subject` (`fix(sim):`, `refactor(timeline):`, `perf(ui):`).
5. **Engine**: damage and cost percentage modifiers classified per DBC aura type and
   stacked accordingly (`spell_mod.go`), suppress flags, a 75% armor reduction cap, a
   crit-reduction pseudostat, base damage and threat spell mods. Talent effects are
   `SpellMod`s attached to spells, not multipliers edited in each spell's file.
6. **Tooling**: the item database generated from DBC (`tools/database/gen_db`, `db2tool`),
   Go-to-TypeScript constants regenerated by a vite watcher, i18n (`ui/i18n`,
   `npm run test:locales`), proto versioning checked with `buf`, a sharded
   `run_tests.yml` on every pull request, Discord webhooks for issues and PRs.

## What from this fork ports, and how

`tbc-new` uses the same talent data scheme as this fork: `ui/core/talents/trees/*.json`
with `fieldName`, `location`, `spellIds`, `maxPoints`, `prereqLocation`; a `<Class>Talents`
proto message whose field numbers follow tree order; `core.FillTalentsProto` with
`TalentTreeSizes`. That decides what is a drop-in and what is a reference.

**Drop-in data** (copy the files, or run one small converter):
- The nine Forever talent trees, `ui/core/talents/trees/*.json`. Our extra keys (`name`,
  `description`, `icon`, `ranks`, `notSimulated`) are harmless; theirs adds `fancyName`.
- The nine `<Class>Talents` proto messages and each class's `TalentTreeSizes`.
- The 31 community builds (`makePresetTalents` in each `ui/<spec>/presets.ts`). Talent
  strings are positional, so they are valid wherever the trees are identical.
- The racial, profession and rule facts, and their sources: `docs/forever_rules.md`.
- The tooltip audit and beta checklist: `docs/forever_beta_checklist.md`.
- The source data and review status under `tools/forever_talents/`.

**Reference, not patches**: the Go implementations in `sim/`. Ours edit multipliers and
register auras against the 2024 Classic core; theirs would be `SpellMod`s on the MoP core.
The rules sheet exists so they can implement from the rule, not from our diff. Same for the
UI: `ui/core` here is the 2024 Classic UI, theirs has moved to per-class/spec modules, i18n
and a different results pipeline.

**Diverged, do not expect to port**: the DPS rankings page (it runs one raid sim with a
player per build, and they removed the raid sim UI), the raid presets glue, the BiS page
(EP over the item database, which they generate differently), and the makefile page
generation (moving to vite here too, below).

## Changes made here to make cherry-picking easier

- Generate the spec pages in vite the way they do, and drop the makefile HTML rule.
- Run the Go tests, the build and the page smoke test on every pull request, as their
  `run_tests.yml` does.
- Conventional commit subjects from here on: `type(scope): subject`.
- Keep the Forever data separable from the engine changes: trees, protos, presets, and the
  two `docs/forever_*.md` files are the data pack; nothing Forever-specific hides in shared
  UI code without a comment naming it.
- Do not chase their log/timeline/UI rewrites. They do not apply to this base and the
  official fork will have them for free.

## The inherited TODOs are open upstream too (checked 17 September)

The sim carries 246 `TODO`s. Roughly 150 are Forever's own - "only rank 1 was seen", "the
demo", "beta will confirm" - and nothing upstream can answer them. The rest came across
with the fork, and it is tempting to assume upstream has since worked them out.

It has not. A pass over 24 of them against `wowsims/classic` master found no value this
fork is missing. The files carrying them are character-for-character identical to
upstream, TODOs included: `sim/common/enchant_effects.go`, `sim/core/attack.go`,
`spell_result.go`, `mana.go`, `energy.go`, `cast.go`, `spell.go`, `consumes.go`,
`sim/encounters/blackwing_lair.go` and others. Every "Proc rate assumed and needs testing"
in `sim/common/item_effects.go` reads the same on both sides, and upstream's own tracker
still lists those rates as untested.

Where the two differ, this fork is ahead rather than behind: it adds `ArmorIgnorePercent`
handling, per-hand Windfury, and a real answer to upstream's `// TODO AQ <=` in Arcane
Missiles. Upstream's extra item registrations are Season of Discovery and AQ content this
fork deliberately omits, some of it carrying SoD-specific proc tuning that would be wrong
to import.

So the inherited TODOs are a shared open question, not a gap. Re-checking is cheap if
upstream moves, but nothing is waiting there to be picked up today.

One practical note for anyone repeating the comparison: this fork is CRLF and upstream is
LF, so a naive diff reports every line as changed. Strip CR first.
